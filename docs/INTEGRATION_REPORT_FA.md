# گزارش ادغام و سخت‌سازی SmartShelf

تاریخ بررسی: ۳ نوامبر ۲۰۲۶

## ۱. فایل‌های مبنا

دو بسته بررسی شدند:

- `smartshelf(2).zip`: سورس کامل‌تر شامل FastAPI، مدل‌های دیتابیس، WebSocket دوربین، موتور ONNX/MobileNet، پایپ‌لاین بینایی ماشین و تست‌ها.
- `shelf-ir-project.zip`: خروجی فرانت‌اند Vercel شامل پنل مدیریت و صفحه آزمایش دو مرجعی. قرارداد `/api/presence` در آن وجود داشت، اما سورس پیاده‌سازی آن API در بسته نبود.

به همین دلیل، API دو مرجعی به‌صورت سازگار با بک‌اند اصلی بازسازی و در همان پایپ‌لاین ادغام شد؛ این پیاده‌سازی ادعای کپی دقیق سورس API مفقودشده را ندارد.

## ۲. ادغام تشخیص دو مرجعی

- صفحه کالیبراسیون در تب تشخیص پنل مدیریت قرار گرفت.
- برای هر Zone، مرجع محصول حاضر و مرجع جایگاه خالی دریافت می‌شود.
- ROI در سطح Zone ذخیره می‌شود.
- ویژگی‌های SIFT/ORB + RANSAC در فیلدهای مرجع دیتابیس ذخیره می‌شوند؛ فایل تصویر خام ذخیره نمی‌شود.
- API احراز هویت‌شده `GET/POST /api/presence` اضافه شد.
- عملیات API شامل `calibrate`، `detect` و `clear` است.
- پایپ‌لاین اصلی در صورت وجود مرجع جدید از موتور دو مرجعی استفاده می‌کند و برای داده‌های قدیمی، موتور HSV/thumbnail را حفظ می‌کند.
- تشخیص دستی صفحه فقط برای تست است و مستقیماً سبد مشتری را تغییر نمی‌دهد.

## ۳. اصلاح خطاهای تشخیص و پایداری

- در موتور قدیمی، اگر فقط یک مرجع موجود بود و تصویر با آن تطبیق نداشت، سیستم ممکن بود حالت مخالف را نتیجه بگیرد. اکنون یک مرجع ناقص همیشه `UNKNOWN` است.
- اختلاف کم دو مرجع یا تطبیق ناکافی، `UNKNOWN` تولید می‌کند.
- فریم نامشخص، پنجره debounce را قطع می‌کند؛ زمان پایداری باید پیوسته باشد.
- محاسبه زمان debounce برای شروع ساعت از صفر اصلاح شد.
- پس از کالیبراسیون جدید، وضعیت Zone و ماشین حالت به `UNKNOWN` بازنشانی می‌شوند تا baseline جدید تثبیت شود.

## ۴. سخت‌سازی ارتباط دوربین و فروش

- مسیرهای شبیه‌سازی ورود مشتری و ساخت نشست جعلی از `/enter` حذف شدند.
- ساخت فاکتور ساختگی در صورت قطع بک‌اند از صفحه مشتری حذف شد.
- fallback ورود ادمین با PIN/توکن ساختگی حذف شد.
- توکن ساختگی `vcl_dev_` دیگر به‌عنوان اتصال دوربین معتبر شناخته نمی‌شود.
- ارسال تصویر/رویداد از طریق `ntfy.sh` و انتقال P2P با PeerJS از مسیر عملیاتی حذف شد.
- موتور قدیمی کلاینتی که محصول نمونه ثابت را به‌صورت رویداد خرید منتشر می‌کرد، از صفحات عملیاتی حذف شد.
- فریم دوربین پس از ۱۰ ثانیه عدم دریافت، دیگر به‌عنوان فریم زنده سرو نمی‌شود.
- حجم، ابعاد و شناسه دستگاه در ورودی فریم محدود/اعتبارسنجی می‌شوند.
- عمر توکن و کوکی مدیر از `TOKEN_TTL_SECONDS` یکسان‌سازی شد.
- PIN چهاررقمی/پیش‌فرض در Production رد می‌شود.

## ۵. ارزیابی مدل شناسایی هویت محصول

گزارش ارزیابی همراه سورس، دقت Top-1 برابر ۵۰٪ روی ۲۰ نمونه را ثبت کرده است. این مدل هنوز برای افزودن قطعی محصول به فاکتور کافی نیست. تشخیص حضور/خالی بودن و شناسایی هویت محصول دو مرحله مستقل هستند. برای استفاده عملیاتی باید دیتاست واقعی هر محصول از زاویه‌ها، نورها و فاصله‌های مختلف افزایش یابد و precision/recall و confusion matrix دوباره ارزیابی شود.

## ۷. موانع انتشار عمومی

نسخه Production فعلی روی `shelf-ir.vercel.app` دست‌نخورده باقی مانده است. دیپلوی جدید انجام نشده، چون تنظیمات واقعی بک‌اند هنوز آماده انتشار عمومی نیستند:

1. فایل `.env` داخل بسته ورودی، PIN چهاررقمی دارد؛ برنامه جدید آن را در Production رد می‌کند. با `python scripts/gen_secrets.py` کلید و PIN جدید بسازید و در `.env` قرار دهید.
2. `PUBLIC_BASE_URL` فعلی روی localhost است. یک URL ثابت HTTPS/WSS برای FastAPI از طریق Tailscale Funnel لازم است.
3. همان URL بک‌اند باید در `frontend/config.js` به‌عنوان `apiBase` ثبت شود.
4. `FRONTEND_PUBLIC_URL` و `ALLOWED_ORIGINS` باید `https://shelf-ir.vercel.app` را شامل شوند.
5. دوربین تبلت باید در محل واقعی با فریم زنده، نور واقعی و ROI نهایی آزمایش شود.
6. تا افزایش دقت شناسایی هویت محصول، صدور فاکتور خودکار بر اساس خروجی مدل ۵۰٪ قابل توصیه نیست.

## ۸. فایل‌های محرمانه حذف‌شده از بسته انتشار

از بسته خروجی `.env`، دیتابیس SQLite و نسخه پشتیبان آن، پوشه گواهی/کلید خصوصی، `.git` و فایل‌های cache حذف می‌شوند. این موارد نباید در بسته عمومی یا مخزن عمومی قرار گیرند.
